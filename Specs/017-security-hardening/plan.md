New-code rule: *file contents an outsider could control are read through this helper or not at all.*

## 5. Status log

- **2026-08-01 (filesystem failures classified by remedy, not by cause).** A plain permissions problem creating the scratch folder escaped unclassified and was reported as *"this is a defect in skillet, not a problem with your project"* — blaming ourselves for the machine's refusal — while the other paid command let the same class escape entirely unhandled. Fixed with a **single stated rule**, written where the next such error will be classified: a broken *layout* is something to fix in the project (bad artifact); the operating system refusing us — permissions, disk, I/O — is something to fix on the machine (environment); anything unanticipated is our bug (internal). Grounded in the modern convention of categorising errors by *what the user must do and who is responsible* rather than technical root cause; the extended Unix I/O codes were considered and rejected as cause-based, non-portable, and rarely consumed — [a modern replacement library abandoned them for user-error vs system-error ranges](https://github.com/square/exit), and [the operative advice is to document whatever codes you return](https://chrisdown.name/2013/11/03/exit-code-best-practises.html). The earlier file-write classification, which called a permissions failure a data problem, is harmonised to the same rule, and the message now carries the remedy (check permissions and disk space). +1 test.
- **2026-08-01 (S15 — a paid command could spend without the harness safety check).** The measured-run command refuses a known-bad or signed-out model program **before** paying; the drafting command, added later, went straight from locating the program to running it — so it could spend against a blocked or unauthenticated setup, and the blocked/not-signed-in refusals were unreachable from it entirely. Fixed by making that check **one shared routine both commands call**, rather than adding a second copy: the security guidance is explicit that a single routine is what prevents "several implementations, most correct and one flawed", and that every path to the same operation must apply the same checks — a description of this bug rather than an analogy ([OWASP access control](https://top10proactive.owasp.org/the-top-10/c1-accesscontrol/)). The measured-run command's behaviour is unchanged (it still relaxes strictness only for its canned offline mode, and still receives the harness details it stamps into records). The drafting command skips the gate only where nothing is spent. **Verified by removing the gate — the test fails; restored, it passes.** +1 test.
- **2026-07-30 (S14 — a drafting evidence id could read files outside the project).** `suggest --from <id>` interpolated the operator's text straight into a path. `appendingPathComponent` treats `/` as a separator and the OS resolves `..` at open time, so `--from ../../../../elsewhere` resolved outside the project; the safe reader refuses symlinks, special files and hard links but does **not** confine a path, so any ordinary `.md` on the machine was readable up to the 1 MiB cap — and the differing errors for present-vs-absent made it an existence oracle. Fixed with two layers: the id is checked against the project's **existing** id rule (a date plus a lowercase-and-dashes name, which structurally cannot contain `/`, `\\` or `.`) **before** it touches a path, and the read then goes through the confining reader with the evidence folder as its base. Paths are built one component at a time. The refusal echoes the id the user typed but never confirms whether anything exists there. **Verified by reverting both guards — the test fails; restored, it passes.** +1 test. (The same round also classified previously-unhandled filesystem errors from the write path as artifact failures, so a permissions problem or a create-race can no longer escape as an unclassified error.)
- **2026-07-30 (LANDMINE FOUND — an eighth property on `SkilletConfig` hangs the YAML decoder).** Adding `suggest:` for F41 wedged the whole test suite: the config-decoding tests stopped emitting events and spun forever, and with them ~7 in-flight tests, so the run never finished. Bisected to a one-line cause — **any** additional stored property on `SkilletConfig` (reproduced with a bare `String?`, so it is not about the new type's shape) makes `YAMLDecoder.decode` loop inside the synthesized `SkilletConfig.init(from:)`; a stack sample shows it spinning in `outlined destroy of SkilletConfig`. With the property removed the same tests pass in 0.003s. The executable decodes fine — only the test bundle wedges — which matches this dependency's known build-unit-sensitive interop fragility (`swift-yaml`, pinned by revision; see the WMO overlay note). **Workaround in place:** `suggest:` is decoded on its own via `ConfigLoader.decodeSuggest`, keeping the main config at its known-good size; `ConfigSupport` gained a shared `configText` resolver so the two reads can never disagree about which file is in play. Pinned by a test. **Anyone adding a new `skillet.yaml` section must know this** — fold it into the main struct and the suite hangs with no failing assertion to point at. Proper fix (upstream report / dependency bump) is a follow-up, tracked as **T13**.
- **2026-07-29 (follow-up: the canonicalization test was vacuous; scope refined).** (1) **The test proved nothing.** It built a project with no recorded sessions, so `triage` took the empty-corpus branch ("record a session — …") — a message that never mentions `skills_root`. The lone negative assertion passed trivially and would have passed with the fix reverted. Rebuilt to exercise **both** interpolation sites (the "review findings under …" hint, which needs a recorded session, and the "add a skill (…)" hint, which needs none) with **positive** assertions on the clean path, so a regression fails loudly. **Verified by construction:** temporarily removing the canonicalization makes the test fail with 5 issues; the original version passed. (2) **Scope refined after research.** The first pass would also have collapsed a lone `.` to empty and thus rejected it — but `.` is the ecosystem's conventional "the directory holding this config" ([TypeScript `rootDir`](https://www.typescriptlang.org/tsconfig/rootDir.html) and peers), a *deliberate* value unlike a blank one, and silently turning an accepted value into an error is a breaking change deserving a [deprecation period](https://docs.getdbt.com/reference/deprecations), not a bug-fix round. Final rule: **trim whitespace** (all-blank → empty → refused by the existing rule), **drop no-op `.` segments** (`./skills` → `skills` — the same doubled-text defect in another costume), **preserve a lone `.`**, and **preserve a leading `/`** so the absolute-path refusal still fires. Tests assert all four plus the two guards. (3) `SessionBundleWriter`'s opening comment documented the reversed layout (`evaluations/<skill>/sessions/…`); behavior was always correct since the destination is caller-supplied, but the comment is now accurate. **+2 tests (one replaced by two) → 596 / 86 green, zero warnings.** Staged, no commit.
- **2026-07-29 (canonicalize `skills_root` at the config boundary).** The value is allowed to end in `/`, and four user-facing messages paste it straight into text (triage ×2, capture, doctor), so `skills_root: skills/` printed `skills//demo/evaluations/findings/` — a path that does not exist, in the very line meant to be copy-pasted. (Path *building* hid it: `appendingPathComponent` normalizes.) Fixed **once at the trust boundary** rather than per message: `ConfigSupport.validated` now canonicalizes before validating — the standing rule that normalization happens where input enters and **precedes** validation ([CERT — Input Validation and Data Sanitization](https://wiki.sei.cmu.edu/confluence/display/java/Input+Validation+and+Data+Sanitization)), so the checks judge the canonical form and every consumer (all five commands) inherits the fix, leaving no trap for the next message someone writes. **Security note:** a leading `/` is deliberately preserved — collapsing it would turn `/etc/` into a relative-looking `etc` and defeat the absolute-path rule S7 exists to enforce; the test asserts both the clean hint and that `/etc/` is still refused. **+1 test → 595 / 86 green, zero warnings.** Staged, no commit.
